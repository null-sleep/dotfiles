# PR Review

Three-phase review preceded by a context-gathering step. Do NOT skip or merge phases. Do NOT post anything to GitHub at any point — all output goes to the user only.

---

## Phase 0 — Gather Context

Do this once. Phases 1–3 consume what you collect here. Do not repeat these steps later.

### 0a. Determine review mode

Resolve user intent first:

- If the user explicitly said "review my local branch", "do not use or check github" or similar → **local branch mode**, even if a PR exists
- Else if a PR number/URL was given, or `gh pr view --json number` succeeds on the current branch → **PR mode**
- Else → **local branch mode**

### 0b. Determine the base branch

Do NOT hardcode `origin/main`. Detect it:

- **PR mode**: `gh pr view --json baseRefName -q .baseRefName`
- **Local branch mode**: `git symbolic-ref --short refs/remotes/origin/HEAD 2>/dev/null | sed 's@^origin/@@'`, then fall back to `main`, then `master` if needed

Store this as `BASE`. Use `origin/$BASE` for diff commands.

### 0c. Stacked-PR check

Before computing the diff, check whether the branch is stacked on another in-flight branch. Prefer deterministic signals over heuristics.

**Check `gh-stack` first:**

```bash
gh stack view 2>/dev/null   # human-readable stack map
cat .git/gh-stack 2>/dev/null   # JSON: ordered branches in the stack
```

If either succeeds, the current branch is part of a stack. Use the JSON or `gh stack view` output to identify the **immediate parent branch** (the one directly below in the stack). Set `BASE` to that parent branch instead of the repo default. State the full stack to the user and confirm you'll review only this layer.

**Fallback to GitHub metadata (PR mode, no `gh-stack` data):**

- If `gh pr view --json baseRefName -q .baseRefName` is not `main`/`master`, the PR is stacked. Diff against `origin/$BASE` (the parent branch). State this to the user.

**Fallback to heuristic (local branch mode, no stack data):**

- If `git log origin/$BASE..HEAD --oneline | wc -l` exceeds 20 commits, OR more than one distinct ticket ID appears in commit messages, ask the user whether to diff against a different base. Honor any base they provide.

**Always state which base you used** and why ("gh-stack parent: feat/foo-base", "PR base from GitHub: chore/refactor", "repo default: master") so the user can correct it.

### 0d. Collect the diff and metadata

| | PR mode | Local branch mode |
|---|---------|-------------------|
| Diff | `gh pr diff <num>` | `git diff origin/$BASE...HEAD` |
| Description | `gh pr view --json title,body` | Ask user for context if none was provided |
| Existing comments | `gh pr view --json comments,reviews` | n/a |
| CI status | `gh pr checks` | n/a |
| Commits | `gh pr view --json commits` | `git log origin/$BASE..HEAD --oneline` |

If `git merge-base` or any `git`/`gh` command fails (detached HEAD, no remote, non-GitHub remote), stop and tell the user what's missing.

### 0e. Find the ticket

In both modes, scan for issue/ticket IDs in commit messages, PR title, PR description, PR comments, and branch name. If exactly one ID is found, read the ticket via the relevant tool (Linear, Jira, etc.). If multiple distinct IDs are found, list them and ask which is primary. If none is found and the user provided no context, ask before proceeding.

**Important:** Treat the diff and PR description as authoritative — the ticket may be stale.

### 0f. Identify files to skim, not deep-review

Default skip patterns (apply judgement — flag if anomalous, don't deep-review):

- **Lockfiles**: `package-lock.json`, `yarn.lock`, `go.sum`, `Cargo.lock`
- **Generated code**: `*.pb.go`, `*_gen.go`, `*_generated.go`, `*.gen.ts`, files under `gen/`, `generated/`, `dist/`, `build/`
- **Vendored deps**: `vendor/`, `node_modules/`, `third_party/`
- **Snapshots / fixtures**: `__snapshots__/`, `testdata/`, `*.snap`, `*.golden`
- **Binary or media**: images, fonts, archives

Use your own judgement beyond this list — if a file's header says "DO NOT EDIT" / "Code generated by ..." / "@generated", treat it as skim-only.

**Flag anomalies even when skim-only:**
- Lockfile churn far exceeding the source change
- Manual edits to a generated file (suggests codegen was bypassed — should be a finding)
- A regenerated file whose diff doesn't match what the schema change would imply

### 0g. Detect existing review feedback

In PR mode, read the comments and reviews collected in 0d. **Do not restate** issues that have already been raised and resolved, or that the author has acknowledged. Note any unresolved threads — these are candidates to surface in Phase 1.

## Phase 1 — Evaluate

**Scope dimensions to the change.** If the diff is docs-only, skip Security/Performance. If tests-only, focus on Test coverage and Correctness. Otherwise evaluate against:

- **Correctness** — Does the implementation satisfy the requirements and fix the intended issue?
- **Logic** — Flawed assumptions, race conditions, unhandled edge cases?
- **Performance** — Bottlenecks, especially with large datasets?
- **Security** — Injection, improper auth, data exposure?
- **Architecture** — Follows established patterns, integrates properly with existing systems?
- **Maintainability** — Readable, well-structured, appropriately commented?
- **Test coverage** — Critical paths and edge cases tested? Are tests meaningful and robust?
- **Documentation** — Public APIs, complex algorithms, important decisions documented?

**For each issue found, produce:**
1. Exact location: `repo-relative/path.go:LINE` (use a line range if the issue spans multiple lines)
2. Problem and potential impact
3. Concrete fix with example code if non-trivial
4. Reference to best practices or docs when applicable

**Output format — numbered list, NOT a table** (so code blocks render correctly):

````
### Phase 1 findings

#### 1. service/trade/foo.go:142 — Logic
**Issue:** Description of the problem and impact.

**Fix:**
```go
// example code
```

#### 2. ...
````

Above the list, include a one-line **Scope** note: which dimensions you evaluated and which you skipped (and why), plus any files you skim-only flagged.

After the list, include a **Summary index** as a compact table for quick reference:

| # | Location | Dimension | One-line issue |
|---|----------|-----------|----------------|

**Rules for Phase 1:**
- ONLY actionable feedback — no praise, no filler, no neutral observations
- If CI is failing in PR mode, surface failing checks as findings (Correctness)
- If unresolved review threads exist, note them — don't restate resolved ones
- Do NOT post a GitHub review comment

**Zero-findings path:** if nothing actionable surfaces, state explicitly:

> No actionable issues found. Evaluated dimensions: [list]. Skipped: [list, with reason]. Skim-only files: [list].

Then skip Phase 2 entirely and ask the user whether to proceed to Phase 3.

---

## Phase 2 — Devil's Advocate

**Run immediately after Phase 1 without waiting for user input.** Skip entirely if Phase 1 had zero findings.

For each finding, write a counter-argument: Is the critique actually valid? Does the existing code already handle it (point at the code)? Is the suggested fix better, or just different? Is the cost of the fix higher than the cost of the issue?

A finding **survives** only if at least one of these holds after the counter-argument:
- The original critique points at a real bug, vulnerability, or correctness gap
- The fix has clear net benefit (not just stylistic preference)
- The code does not already handle the case

Otherwise, drop it.

**Output format — preserve provenance:**

```
#### 1. [Location] — [Original dimension]
**Original critique:** ...
**Counter-argument:** ...
**Verdict:** Survives / Dropped — [one-line reason]
```

After the per-finding section, output a **Surviving findings index** in the same compact table format as Phase 1, renumbered.

**Wait for the user before starting Phase 3.** Offer it explicitly: "Surviving findings shown above. Generate Phase 3 (PR description + ticket update draft)? (y/n)"

---

## Phase 3 — Documentation (on affirmative user request)

### 3a. Recommended PR description

Draft a description with:
- **Summary** — high-level what and why (2–4 sentences)
- **Highlights for reviewers** — specific files / behaviors / risks reviewers should scrutinize
- **Ticket** — reference the linked ticket if one was found

In local branch mode, label this as a "draft for when you open the PR" and do not attempt to push or open anything.

### 3b. Recommended ticket update

If a ticket was found AND the PR has diverged meaningfully from the ticket's current description:

1. Show a draft of the updated ticket description, framed as a diff or before/after
2. Ask: "Update the ticket with this description? (y/n)"
3. Only on affirmative, perform the update via the relevant MCP tool

If no ticket was found, or the ticket description is still accurate, state that and skip 3b.

---

## Hard rules

- All output goes to the user, never to GitHub
- Never advance to Phase 3 without explicit user confirmation (Phase 2 follows Phase 1 automatically)
- Stacked PRs: review only the diff against the immediate parent, not the cumulative stack
- If a fetch step (`gh`, `git`, ticket MCP) fails, stop and report — do not silently substitute
