# RTK multi-harness integration plan

## Problem

RTK is installed and works transparently in Claude Code through the guarded
`PreToolUse` hook in `claude/.claude/settings.json`, but the other coding
harnesses configured by this repository do not currently have equivalent
command-rewrite integrations:

- Cursor Agent has no `~/.cursor/hooks.json` RTK `preToolUse` hook.
- pi has no RTK `tool_call` extension.
- opencode has no RTK `tool.execute.before` plugin.
- omp has no upstream RTK target. Automatic integration is therefore an
  optional, evidence-gated custom extension rather than part of the default
  rollout.

OpenRouter is not another integration target. It is the model provider used by
opencode, pi, and omp; RTK acts at each harness's shell-tool boundary, before
provider traffic. Herdr and sidekick.nvim are launchers/multiplexers, so they
inherit the integration of whichever harness they start and need no RTK hook.

The installed RTK is `0.43.0`; Homebrew currently offers `0.45.0`. The Brewfile
already carries unpinned `brew "rtk"`, so upgrading is a machine action, not a
formula change.

## Outcome

One `brew bundle`/Stow checkout supports transparent RTK rewriting in Claude
Code, Cursor Agent, pi, and opencode without allowing RTK's initializer to
rewrite repo-owned configuration or install a duplicate Claude hook. omp keeps
its native structured-tool path and uses RTK explicitly for selected noisy
Bash commands unless measurement justifies maintaining a custom adapter.

Each adapter remains deliberately thin: it only sends the original shell
command to `rtk rewrite` or `rtk hook <host>`. All rewrite rules and output
filtering remain owned by the installed RTK binary.

## Decisions

- **Keep the existing Claude hook unchanged.** Its guarded command is portable
  across machines without RTK. RTK's own `--show`/`gain` detection may report
  it as absent because it recognizes only the exact unguarded command, but
  `rtk verify` confirms the native hook and its tests pass.
- **Do not run `rtk init -g --agent cursor` against the live config.** With
  RTK 0.43.0, its dry run attempted to append a second unguarded Claude hook
  because it did not recognize the repo's guarded wrapper. Use the upstream
  Cursor hook payload, but deploy it through this repo.
- **Track supported static adapters with their owning Stow packages.** Cursor's
  hook, pi's extension, and opencode's plugin are durable policy, not
  credentials or mutable runtime state. `stow --no-folding` already keeps each
  parent directory real, allowing these links to coexist with each harness's
  machine-written files.
- **Vendor thin generated adapters, not RTK internals.** The pi and opencode
  files generated by `rtk init --dry-run` delegate to `rtk rewrite`; they do
  not duplicate the rewrite registry. Preserve a header recording the RTK
  version used to refresh them and the upstream generation command.
- **Do not add an omp adapter by default.** omp already provides compact,
  structured `read`, `grep`, `glob`, LSP, DAP, GitHub, and hashline-edit tools;
  RTK can affect only commands sent through `bash`. There is no upstream
  `--agent omp` target, and the pi adapter is not source-compatible because omp
  uses `@oh-my-pi/pi-coding-agent`. Prefer explicit `rtk ...` calls for noisy
  builds/tests/logs, then add a custom extension only if measured Bash volume
  and savings justify owning that unsupported integration.
- **Fail open when RTK is absent, old, times out, or declines a rewrite.** A
  missing optimizer must never break a shell command. Log one concise load-time
  warning for a missing/unsupported binary; unexpected per-call errors pass the
  original command through.
- **Never rewrite an already-prefixed `rtk ...` command.** This prevents loops
  and makes explicit `rtk proxy ...` or `rtk gain` calls authoritative.
- **Honor `RTK_DISABLED=1` in pi and opencode adapters.** This provides a
  session-local escape hatch without changing tracked configuration. Verify
  whether the upstream Cursor hook already honors it before documenting it for
  Cursor. An optional future omp adapter must implement the same escape hatch.
- **Keep native file/search tools native.** RTK hooks only shell/Bash calls.
  Cursor/pi/opencode/omp `read`, `grep`, `glob`, LSP, and similar structured
  tools should not be routed through RTK.

## OMP decision framework

### What RTK can and cannot improve in omp

OMP's structured tools should remain the first choice. `read`, `grep`, `glob`,
`lsp`, `debug`, `pr://`/`issue://`, `github`, `ast_edit`, and hashline `edit`
already return bounded, machine-structured results. They never cross the Bash
boundary, so an RTK hook cannot compress them. Replacing them with shell
commands solely to reach RTK would discard structure, source anchors,
permission semantics, or tool-specific recovery behavior.

The plausible RTK surface is narrower:

- test and build commands with repetitive success output (`cargo test`,
  `pytest`, `go test`, `npm`/`pnpm` test scripts, compilers and linters);
- Git commands issued through Bash instead of omp's higher-level facilities;
- Docker/Kubernetes/AWS output and long application logs;
- repository-specific commands for which RTK has a trusted TOML filter.

Short probes, interactive programs, binary-producing commands, commands whose
exact stdout is the deliverable, and unsupported commands should remain raw.
Use `rtk proxy <command>` only when tracking without filtering is useful; it is
not a substitute for preserving exact output when the caller needs every byte.

### Why explicit use is the default

- OMP discovers `.claude` context and `~/.claude` instructions, so its model can
  already be instructed to choose `rtk cargo test`, `rtk git status`, or
  `rtk test <command>` for known-noisy shell work. No extension is required for
  that path.
- Explicit invocation makes the compression decision visible at the callsite
  and leaves unusual/debugging commands raw.
- RTK upstream does not test an omp adapter. OMP's extension event types,
  package namespace, tool approval flow, and task/subagent runtime can change
  independently from pi's supported adapter.
- Automatic rewriting adds a pre-execution dependency and can hide context a
  debugging session needed, even when RTK's filters are generally safe and
  recoverable through tee/history facilities.
- OMP's task agents run in-process with their own extension runners. A custom
  hook must be verified in both main and task contexts rather than assumed to
  inherit main-session behavior.

### Evidence required before adopting an automatic adapter

Run a representative OMP-only observation period rather than using Claude's
global RTK totals. Capture at least:

1. the number of OMP Bash calls versus structured-tool calls;
2. which Bash command families dominate raw output;
3. raw bytes/tokens and RTK-filtered bytes/tokens for those commands;
4. whether filtered output preserved every failure, warning, exit status, and
   recovery path needed to finish the task;
5. how often the model already selected explicit `rtk ...` from discovered
   instructions;
6. main-session versus task/subagent Bash volume.

Prefer `RTK_HOOK_AUDIT=1`/`rtk hook-audit` when the installed version can
attribute events cleanly. Otherwise bracket isolated OMP sessions with
`rtk gain --history` and keep a small command ledger; cumulative global totals
mix Claude, Cursor, pi, opencode, and manual terminal use and are not evidence
for omp adoption.

Adopt automatically only when all of these are true:

- OMP repeatedly emits substantial supported-command Bash output after native
  structured tools and explicit RTK use are already preferred;
- measured savings are material to full-session context, not merely a large
  percentage of a tiny Bash slice;
- representative failures remain diagnosable, including access to unfiltered
  recovery output;
- the adapter works in main, headless, and task/subagent contexts without
  changing approval decisions or native tool behavior;
- maintaining an omp-specific adapter across upgrades is worth the remaining
  savings.

If any condition fails, keep explicit invocation and record “no adapter” as the
successful outcome. Absence of an extension is a decision, not unfinished
integration.

## Implementation phases

### Phase 1 — Refresh and capture upstream adapters

- [ ] Run `brew upgrade rtk`; record `rtk --version` in implementation notes.
- [ ] Re-run dry previews for Cursor, pi, and opencode with global `-v` before
      `init`; confirm paths and payloads without writing:

  ```bash
  rtk -v init -g --agent cursor --dry-run
  rtk -v init -g --agent pi --dry-run
  rtk -v init -g --opencode --dry-run
  ```

- [ ] Compare the upgraded dry-run payloads with the 0.43.0 payloads captured
      during planning. Pay particular attention to rewrite exit codes,
      timeout handling, permission decisions, and supported host event names.
- [ ] Run `rtk init -g --agent cursor --show` and `rtk verify`; preserve the
      existing Claude hook rather than accepting any proposed settings patch.
- [ ] Inspect `rtk rewrite --help` and `rtk hook cursor --help` from the upgraded
      binary. Treat those installed interfaces as authoritative for adapters.

### Phase 2 — Cursor hook

- [ ] Add the upstream Cursor `hooks.json` payload under the `cursor` Stow
      package.
- [ ] Confirm the file does not collide with a machine-local regular
      `~/.cursor/hooks.json`. If a divergent file exists, stop and reconcile it
      rather than overwriting or adopting it.
- [ ] Restow with `stow --no-folding cursor` and confirm the live file resolves
      to this checkout.
- [ ] Validate JSON with `jq empty` and assert exactly one `Shell` RTK
      `preToolUse` entry.
- [ ] Confirm Cursor's existing status line and Claude-derived sidekick
      notification hooks remain unchanged; RTK owns only shell rewriting.

### Phase 3 — pi extension

- [ ] Add the refreshed upstream-generated `rtk.ts` to
      `pi/.pi/agent/extensions/` with no local rewrite rules.
- [ ] Check imports against installed pi `0.84.1` or newer and format using the
      repository's existing TypeScript style.
- [ ] Restow `pi`; confirm the extension coexists with `claude-footer.ts`,
      `nvim-notify.ts`, package-installed extensions, and Herdr's machine-local
      extension.
- [ ] Launch pi and verify the extension loads without a startup warning.
- [ ] Exercise one rewritten Bash command and one unsupported command that must
      pass through unchanged.
- [ ] Repeat with `RTK_DISABLED=1`; the command must remain unmodified.

### Phase 4 — opencode plugin

- [ ] Add the refreshed upstream-generated plugin beside
      `nvim-notify.ts`; do not add plugin registration to `opencode.json` unless
      current opencode documentation proves directory auto-discovery is no
      longer sufficient.
- [ ] Confirm compatibility with installed opencode `1.18.10` or newer and its
      current `tool.execute.before` payload.
- [ ] Restow `opencode`; ensure neither `opencode.json` nor credentials are
      rewritten.
- [ ] Launch opencode and verify both plugins load without warnings.
- [ ] Exercise rewritten, passthrough, already-RTK-prefixed, and disabled paths.

### Phase 5 — omp measurement and adoption decision

- [ ] Keep the initial omp configuration unchanged: no RTK extension and no
      Bash interception. Confirm its discovered Claude/RTK instructions are
      visible, but do not confuse instructions with a transparent hook.
- [ ] Establish the native-tool baseline. Run representative maintenance,
      debugging, review, and implementation tasks and classify every operation
      as a structured omp tool, a short/raw Bash call, or a noisy Bash call
      supported by RTK.
- [ ] For noisy supported commands, compare three paths using the same command
      and inputs:
  - raw Bash;
  - explicit specialized RTK (`rtk cargo test`, `rtk git status`, etc.);
  - `rtk proxy` only when unfiltered tracked output is a useful control.
- [ ] Record command family, context (main or task agent), raw and filtered
      size, exit status, whether failures/warnings survived, and whether full
      recovery output was available. Do not use global cumulative savings as
      omp evidence.
- [ ] Check whether discovered instructions cause omp to choose explicit RTK
      reliably for recurring noisy commands. If they do, prefer that visible,
      selective behavior over automatic interception.
- [ ] Exercise debugging-sensitive cases—failing builds, partial test failures,
      compiler warnings, long logs, pipelines, exact-output commands, and an
      unsupported command—to identify information loss or unsafe rewrites.
- [ ] Apply the adoption gate in “OMP decision framework” and record one of two
      explicit outcomes:
  - **Default: no adapter.** Document recommended explicit commands and stop;
    this completes omp evaluation.
  - **Adopt:** proceed only when the measured remaining savings are material
    and every correctness/maintenance condition passes.

If and only if the outcome is **Adopt**:

- [ ] Read the installed omp extension types/source for `ExtensionAPI.exec`,
      `tool_call`, command-input revision, handler context, cancellation, and
      task-agent extension loading. Do not assume pi's helper exports or
      `ctx.signal` exist in omp.
- [ ] Add `omp/.omp/agent/extensions/rtk.ts` as the smallest native adapter:
  - import types from `@oh-my-pi/pi-coding-agent`;
  - probe `rtk --version` once at load;
  - intercept only `event.toolName === "bash"`;
  - ignore empty, already-prefixed, and `RTK_DISABLED=1` commands;
  - call `rtk rewrite <original-command>` with a bounded timeout;
  - accept only documented rewrite exit codes and non-empty output;
  - replace only `input.command` through omp's documented revision mechanism;
  - preserve approval behavior and pass the original command through on every
    failure.
- [ ] Verify main, headless, and task/subagent contexts. Do not gate on
      `ctx.hasUI`: task-agent Bash output also consumes model context.
- [ ] Confirm native structured tools remain untouched and repeat every
      baseline correctness case through the adapter.
- [ ] Add the adapter to omp's managed-files documentation and record the RTK
      and omp versions against which the unsupported port was verified.

### Phase 6 — Documentation and invariants

- [ ] Update README navigation and the RTK section without breaking the
      existing `#rtk-token-optimizer` link.
- [ ] Update the Cursor, pi, and opencode managed-files tables plus
      fresh-machine commands. Update omp documentation with the no-adapter
      recommendation and evaluation procedure; add an omp managed file only if
      Phase 5 reaches **Adopt**.
- [ ] Update the Brewfile comment.
- [ ] Extend or add focused shell invariants for configuration that can regress
      silently:
  - exactly one guarded Claude RTK hook;
  - exactly one Cursor RTK Shell hook;
  - valid Cursor JSON;
  - expected pi/opencode adapter files present under their owning Stow packages;
  - no adapter contains hard-coded Homebrew or home-directory paths;
  - no omp RTK adapter present unless Phase 5 records **Adopt**.
- [ ] Avoid tests that merely snapshot generated TypeScript source. Behavioral
      smoke checks below defend the observable contract.

## Verification

### Static checks

- Run the existing Claude settings invariant suite.
- Parse every changed JSON file with `jq empty`.
- Run the repository's applicable shell formatter/linter checks for changed
  shell tests or setup scripts.
- Run TypeScript diagnostics or each harness's extension/plugin loader against
  the pi and opencode adapters; no unresolved host-package imports. Include omp
  only if Phase 5 reaches **Adopt**.
- Run `rtk verify`; expect all RTK hook-engine tests to pass.
- Run `rtk hook check 'git status'`; expect `rtk git status`.
- Run `rtk hook check` on an intentionally unsupported command; expect the
  documented no-rewrite result, not an invented generic wrapper.

### End-to-end smoke matrix

For each transparently supported harness, start a fresh one-shot or interactive
session with an explicit instruction to use its shell/Bash tool for
`git status`. Do not infer success from adapter loading alone.

| Harness | Trigger | Required evidence |
|---|---|---|
| Claude Code | Bash `git status` | Existing hook still rewrites once; no nested `rtk rtk` command |
| Cursor Agent | Shell `git status` | Cursor hook fires and RTK history/audit records the rewrite |
| pi | Bash `git status` | pi extension rewrites; session continues normally |
| opencode | Bash/shell `git status` | plugin rewrites; nvim notification plugin still loads |

Use `RTK_HOOK_AUDIT=1` plus `rtk hook-audit` if supported by the upgraded
version; otherwise compare `rtk gain --history` immediately before and after
each isolated smoke. Evidence must identify the host and command rather than
relying on the cumulative global count.

For pi and opencode, repeat one smoke with `RTK_DISABLED=1` and verify no new
rewrite record appears. Run one explicit `rtk gain` command through each
harness and confirm it is not rewritten recursively.

OMP has a separate evaluation smoke: run raw and explicit-RTK versions of a
representative noisy command and confirm both correctness and measurable
savings. Do not expect plain `git status` to rewrite automatically under the
default no-adapter decision. If Phase 5 reaches **Adopt**, add omp to the
transparent matrix and repeat in a task/subagent plus with `RTK_DISABLED=1`.

### Regression checks

- Cursor status line still renders after adding `hooks.json`.
- pi's Claude-shaped footer, theme, npm extensions, and nvim notification bridge
  still load.
- opencode still resolves its configured OpenRouter model and both plugins.
- omp still resolves model roles/config and its nvim notification extension;
  under the default decision it loads no RTK extension and explicit
  `rtk ...` Bash commands still work.
- `printenv OPENROUTER_API_KEY` and model lists are unchanged; no provider or
  credential file is touched.
- Herdr/sidekick-launched sessions exercise the same per-harness integration;
  no Herdr-specific RTK files are introduced.
- `rtk gain` may retain its known false “No hook installed” warning for the
  guarded Claude hook, but `rtk verify` and the end-to-end Claude smoke must
  succeed.

## Cleanup

- [ ] Remove any machine-local RTK adapter/plugin created during experiments if
      a tracked Stow link now owns that path. Remove every omp prototype when
      Phase 5's outcome is **no adapter**.
- [ ] Remove dry-run scratch files and hook-audit environment overrides.
- [ ] Confirm no live config was replaced by an unreviewed `rtk init` patch.
- [ ] Review all README paths and commands from a fresh-machine perspective.
- [ ] Record the RTK version used to refresh the vendored adapters in their
      headers or the RTK README section so later upgrades can diff regenerated
      output deliberately.

## Acceptance criteria

- Claude retains exactly one guarded RTK hook.
- Cursor, pi, and opencode transparently rewrite a supported shell command
  through RTK and preserve unsupported commands.
- No adapter rewrites `rtk ...` recursively.
- Missing RTK and `RTK_DISABLED=1` fail open where supported.
- OMP's evaluation records measured Bash scope, correctness, savings, and an
  explicit adopt/no-adapter decision. The default no-adapter outcome documents
  explicit RTK usage and leaves native structured tools unchanged.
- If omp is adopted, its adapter additionally passes main/task/headless,
  recursion, disable, failure, approval, and native-tool regression checks.
- OpenRouter, Herdr, sidekick.nvim, credentials, and mutable harness settings
  require no RTK-specific changes.
- Every durable integration is tracked in the appropriate Stow package and is
  documented in README.md.
- Fresh-machine instructions avoid RTK's duplicate-Claude-hook patch path.
